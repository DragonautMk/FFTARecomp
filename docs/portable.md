# Desktop portable editions

## Start on Ubuntu / Linux x86_64

Extract `FFTARecomp-linux-portable.tar.gz` into a writable folder:

```bash
tar -xzf FFTARecomp-linux-portable.tar.gz
cd FFTARecomp-portable
./FFTARecomp
```

This is a native executable; Wine is not needed. The archive preserves execute
permissions. If a filesystem strips them, run `chmod +x FFTARecomp recomp`.
A graphical desktop and the system ALSA (`libasound.so.2`) and udev
(`libudev.so.1`) runtime libraries are required. The direct host-built archive at
`dist/FFTARecomp-linux-portable.tar.gz` is tested on Ubuntu 26.04 x86_64 and
requires glibc 2.43 or newer. The separately exported Docker build is under
`dist/docker-linux/`; its base and linked libraries are recorded in
`BUILD-INFO.txt` (see [Docker builds](docker.md)). Use a
Linux filesystem that allows execution (USB mounts with `noexec` cannot launch
executables). Portable describes app storage, not a fully static Linux binary.

## Closing on Ubuntu / Wayland

A shutdown crash reported on Ubuntu 26.04 with AMD RADV/Mesa 26.0.8 was
reproduced after the cartridge save had been written. Winit consumes its event
loop on return; releasing the remaining wgpu EGL resources afterwards used an
already closed Wayland display, even though rendering selected Vulkan. The
runtime now stops audio and releases GPU/software surfaces, contexts and the
window in its final event-loop callback, including error exits. Window close
and menu Quit use that same cleanup path.

With an older executable, a log ending in `saved ...ffta.sav` followed by
SIGSEGV matches this failure; the save write had completed before the crash.
Update the executables from a fresh archive while the game is closed, keeping
your existing `Data` folder, ROM and `portable.txt`.

## Start on Windows

Extract `FFTARecomp-windows-portable.zip` into a writable folder and run
`FFTARecomp.exe`.

## Shared storage

There is no installation step, registry registration or
shortcut creation. On first launch select your own supported FFTA USA/Europe
ROM; the launcher copies it to `ffta.gba` beside the executables. Cancelling
leaves setup unfinished. You can also put `ffta.gba` there manually. The first
launch builds its translation cache using bundled TinyCC; no compiler install
is needed. ROMs and BIOS images are not distributed.

The `portable.txt` marker beside both executables enables portable storage.
Paths resolve from the actual executable, including symlink resolution, rather
than the shell's working directory. The launcher and runtime do not fall back
to an installed ROM, per-user settings, cache or remembered save in this mode.
An unwritable folder produces an error rather than redirecting save data.

| Location | Contents |
| --- | --- |
| `ffta.gba` | Your selected ROM copy |
| `Data/config/input.cfg`, `av.cfg` | Controller/menu bindings, audio/video/FPS settings |
| `Data/config/labels/` | Optional developer label accumulators |
| `Data/cache/` | Regenerable native translations |
| `Data/saves/ffta.sav` | Raw cartridge progress, shared when switching FFTA ROMs |
| `Data/saves/SaveBackups/ffta.sav/` | Two startup copies of cartridge progress |
| `Data/saves/SaveStates/<ROM SHA-256>/` | Nine state slots including previews |
| `gba_bios.bin` or `Data/config/gba_bios.bin` | Optional user BIOS |
| `play-error.log` | Startup/runtime error details |
| `play.log` (Linux) | Last runtime output |

The optional developer `play --rom-data` path prepares decoded game metadata
under `Data/resources/<ROM SHA-256>/v1/e2-d1/`. A relative `current` file selects
a verified immutable generation, so moving the whole bundle reuses it. Missing
or corrupt base data are regenerated without modifying saves, native caches or
future user mods. `FFTA_RESOURCES_DIR` explicitly overrides that root. The flag
also consumes the decoded OBJ metadata; normal startup awaits the remaining
scene/performance gates. Resource files are private game data, not distributed.

Close the game before copying or moving **the whole folder**, including
`portable.txt`, `Data`, ROM, TinyCC and licenses. Paths generated by portable
mode contain no remembered absolute installation directory. Removing only
`Data/cache` is safe while closed; the next launch rebuilds it. Do not run two
instances against the same data folder. External environment overrides such
as `FFTA_SAVE_PATH`, `GBA_RECOMP_BIOS` and `FFTA_TCC_LIBRARY` are still explicit
user choices and can refer outside the bundle; remove them for a self-contained
folder. A USB drive must be writable and have room for cache and state files.
When copying progress between Windows and Linux editions, copy saves/settings
and slot directories rather than executables; let each edition build its own
cache. Linux native translations use `.so`, Windows uses `.dll`.

For debugging, [isolated sessions](debug_sessions.md) create a separate portable
copy from the selected case. Their saves, settings, snapshots, resources and
cache stay inside the copy, and the normal game remains paused. Menu-created
copies live under `Data/debug-sessions/`; retain or move the whole closed folder.

## Import existing progress and settings

Nothing is silently moved from an earlier installation. With both games closed:

1. Keep a separate copy of your original `.sav` and any existing destination.
2. Copy your cartridge save to `Data/saves/ffta.sav` (create directories if needed).
   This is raw GBA save memory, not an emulator save state. The tested EUR save
   is 64 KiB; device/emulator and game-edition compatibility still apply.
3. Optionally copy `input.cfg` and `av.cfg` from
   `%APPDATA%\FFTARecomp\` to `Data/config/`. On Linux the source is
   `$XDG_CONFIG_HOME/FFTARecomp/` or `~/.config/FFTARecomp/`.
4. To retain state slots, copy the previous `SaveStates` directory beside
   `ffta.sav`, keeping its ROM-hash subdirectories. State ROM/BIOS/version checks
   still apply. To retain backups, copy the old save's backup subdirectory into
   `Data/saves/SaveBackups/ffta.sav/`, preserving filenames.

On Linux the old shared save pointer is under
`$XDG_DATA_HOME/FFTARecomp/` or `~/.local/share/FFTARecomp/`.
The older installed Windows save location is recorded in
`%LOCALAPPDATA%\FFTARecomp\shared-save-path.txt`, or is beside the installed ROM
if none was remembered. Portable mode ignores that pointer. To export progress
back to another recompilation or a GBA transfer tool, copy `Data/saves/ffta.sav`
after closing the game. See [backup recovery](save_backups.md) and
[state slots](save_states.md).

## Build

For a Linux build without installing compiler/development dependencies on the
host, run `bash scripts/linux/build_linux_docker.sh`. It exports a separate artifact
to `dist/docker-linux/` using Rust 1.94.0 on Debian Bookworm. See
[Docker builds](docker.md) for caches, output and runtime requirements. The direct
Ubuntu 26.04 archive described above remains a separate host-built artifact.

On Windows with Docker Desktop in Linux-containers mode, run
`.\scripts\windows\build_docker.ps1` from PowerShell. It exports a standalone Windows
ZIP to `dist/docker-windows/`; `-Platform linux` builds the Linux tar.gz instead.
On Linux, `bash scripts/linux/build_windows_docker.sh` produces the same Windows ZIP.
See [Docker builds](docker.md) for host/container distinctions and test scope.

For a native Windows desktop package without Docker, run
`.\build-all.ps1 -SkipLinux -SkipAndroid`. Install Rust with its target linker,
Python3.11+ and a host GCC/Clang for TinyCC first.
For a native Linux release, install Rust, a C compiler, pkg-config and ALSA/udev
development headers, then run `bash scripts/linux/package_ffta_linux.sh`. The output is
`dist/FFTARecomp-linux-portable.tar.gz`. The shared packaging implementation is
`scripts/package_ffta_portable.py --platform linux`; it accepts `--runtime-dir`.
Both native wrappers use `scripts/build_desktop.py`. It reads the two executable
paths from Cargo's JSON output, checks the requested Windows/Linux x86_64 format,
builds TinyCC in that same directory and gives it explicitly to the packager.
`CARGO_TARGET_DIR` and configured target subdirectories therefore cannot silently
select older `target/release` files. Cargo/TinyCC failure stops packaging.
Plain Cargo builds only the executables. When packaging manually, pass the
actual directory to `--runtime-dir` and build TinyCC there with `--output`.
`build-all.ps1` without the switches also builds Linux/Steam Deck installers and
Android; `-SkipAndroid` alone retains Linux. Those steps require the separate
cross compiler/sysroot/pkg-config and Android SDK/NDK/JDK described in their
scripts. The Windows-to-Linux helper uses the lockfile and retains its own
target directory. `AndroidPort/` remains a separate source tree.
The packaging script selects runtime/compiler/docs/licenses explicitly and
never includes an existing `Data` folder, ROMs, saves or generated translations.
Without the marker, existing installed-mode storage remains supported.

The desktop bundles include the [Atlas menu guide](menu_clan_atlas.md) and
[9/99-slot guide](extended_saves.md); the same public-file list is available in
both Docker build contexts. Build-method checks and their limits are recorded
in [Docker/build validation](docker.md#build-method-verification-30-october-2026).

## Validation

Windows GNU release builds and 68 tests (26 input/config, 42 runtime) passed
under Wine; two optional ROM-specific runtime tests were not run. A simulated
XInput check launched the actual wrapper from an unrelated working directory
with spaces in the bundle path, saved a preview slot, moved the folder, then
loaded that slot and reused the unchanged translation cache. Startup backups
remained limited to two copies. Existing installed AppData file hashes and
modification times were unchanged. A separate first-setup check selected the
ROM through the file dialog, verified its copied bytes, and displayed the
portable config's internal-only FPS overlay instead of the installed config.
Native Windows, physical controllers and the full multi-platform PowerShell
build sequence were not tested in this Linux environment.

### Native Linux validation

The native release and bundled TinyCC were built on Ubuntu 26.04 x86_64.
`ldd` resolved every dependency; ELF version inspection found a glibc 2.43
requirement in the runtime (the wrapper requires 2.39). The runtime uses the
system ALSA and udev libraries. Missing ALSA build metadata was supplied by an
Ubuntu development package extracted under ignored `target/`, without changing
system packages; ordinary developer builds should install the development
prerequisites or provide equivalent pkg-config paths.

26 input/config and 41 runtime tests passed natively; two optional runtime tests
were ignored. Native X11 gameplay and the portable FPS setting were observed on
the local desktop. The full keyboard save/load and relocation check ran on Xvfb
with Mesa llvmpipe: launch the actual wrapper from an unrelated working folder,
save slot 1 with its preview, close normally, move the whole bundle, relaunch,
load the slot and close normally again. The cache bytes/mtime were reused,
backup copies numbered one then two, and per-user config/cache/data files did
not change. The first-launch ROM was preplaced for this Linux check. Physical
controllers, native Wayland interaction and older distributions were not tested.
The shared Windows ZIP entry point also passed archive/input verification after
the packaging refactor.

### Wayland shutdown regression

On Ubuntu 26.04 / GNOME Wayland, AMD Radeon 780M, RADV/Mesa 26.0.8,
a temporary local test injected `WindowEvent::CloseRequested` after 180 guest
frames. The original code reproducibly faulted in `libwayland-client`, called
from `libEGL_mesa`, after the save write. With cleanup in `exiting`, GDB reported
normal process exit; two additional runs through the actual launcher saved and
exited with status 0. This used native Wayland/Vulkan and the real audio stream
(muted). The temporary injection was removed before packaging; this was an
automated close-event test, not a physical title-bar click. Physical-controller
and native Windows shutdown checks remain unverified for this change.


## Shared debugging tools in the portable archive

The package now includes the [common five-flow guide](debug_tools.md), detailed
debug docs, offline Python/templates and PowerShell/Bash launchers. The runtime
does not require Python for its built-in commands. Python3.11 or an explicitly
prepared Docker image is needed only for offline homepage/artifact/campaign tools.
Read the guide's Wine/native-Windows/Linux matrix; packaging alone establishes
no platform or gameplay acceptance. Audit/watch require an audit-enabled runtime.

Run scripts/windows/debug_runtime.ps1 COMMAND... or
bash scripts/linux/debug_runtime.sh COMMAND... from any working directory;
relative runtime paths resolve from the selected bundle. Runtime command logs
live in Data/config/debug-logs; offline launcher logs in target/build-logs.
PowerShell artifact/campaign -Docker precedes the tool command and all Python
flags are forwarded without PowerShell common-parameter interception.

PACKAGE-MANIFEST.json lists exact distributed file hashes and original-input
hashes. Public files/licenses/scripts/docs are selected explicitly, without
scanning personal Data or the runtime directory. Data is created empty.
Repository-only references in distributed docs become labelled plain text;
third-party notices remain byte-identical. No ROM/BIOS, snapshots, SRAM,
recordings, diagnostics, native cache or generated game source is packaged.

Host distribution builds should remap compiler source paths before packaging:
Rust --remap-path-prefix for checkout/home/cache roots, and TinyCC/build.py
maps its source and adapter roots with -ffile-prefix-map. The shared packager
accepts repeatable --private-prefix PREFIX to reject embedded UTF-8/UTF-16LE
private paths before replacing the previous archive. It never rewrites binaries;
the manifest records only the number of prefix checks. DBG-22 uses this guard
with its isolated remapped Windows binaries.
